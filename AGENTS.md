# VeriPay

Peer-to-peer conditional payments. Auth0 for authentication, Stripe Checkout
and Connect for money movement, Supabase Postgres for storage.

The repository currently contains the **scaffold only**. Deals, payments,
payouts and authentication are not implemented.

## Repository structure

```text
apps/
  api/       Express 5 HTTP API. Application factory + server entrypoint.
  web/       React 19 + Vite 8 client. Placeholder UI.
packages/
  shared/    Isomorphic domain primitives, error codes, API contracts, Zod schemas.
  database/  Drizzle ORM client, Supabase config parsers, migrations.
  config/    Shared tsconfig bases, ESLint flat config, Prettier config.
docs/        Architecture, environment and tooling notes.
.agents/skills/  Repository-local agent skills.
```

## Commands

Run everything from the repository root.

| Command                                   | Purpose                                           |
| ----------------------------------------- | ------------------------------------------------- |
| `npm run dev`                             | Package watcher + API + web together              |
| `npm run dev:api`                         | API only, on `http://localhost:8787`              |
| `npm run dev:web`                         | Web only, on `http://localhost:5173`              |
| `npm run build`                           | Build packages, then API, then web                |
| `npm run typecheck`                       | Build packages, then `tsc --noEmit` per workspace |
| `npm run test`                            | Vitest across all four test projects              |
| `npm run lint` / `npm run lint:fix`       | ESLint                                            |
| `npm run format` / `npm run format:check` | Prettier                                          |
| `npm run db:generate`                     | Generate migration SQL from the Drizzle schema    |
| `npm run db:migrate`                      | Apply pending migrations                          |

`packages/shared` and `packages/database` compile to `dist/` and are consumed
as ordinary npm packages, so `build:packages` runs first in `build`,
`typecheck` and `dev`. If an import of `@veripay/shared` looks stale, rebuild
the packages.

## Architectural boundaries

These are enforced by `no-restricted-imports` in `eslint.config.js`. A wrong
import fails `npm run lint`.

- **`packages/shared` must stay isomorphic.** No `node:*`, `react`, `express`
  or `postgres` imports. Both the API and the browser bundle depend on it.
- **Backend code must not import frontend modules.** No `react`/`react-dom`
  and nothing from `apps/web` inside `apps/api` or `packages/`.
- **The browser must never reach the database.** `apps/web` cannot import
  `@veripay/database`, `express`, `pino`, `postgres` or `node:*`.
- **The application factory is separate from the server.** `src/app.ts` builds
  and returns an `Express` instance; only `src/server.ts` calls `listen`. Add
  middleware and routes in the factory so Supertest keeps exercising them.
- **Nothing reads `process.env` directly.** `loadEnv(source)` and the database
  config parsers take an explicit source object and are called once at the
  edge; the resulting typed object is passed down.

## Domain rules

### Money is always integer minor units

Every monetary amount — in memory, in the database, on the wire, and at the
Stripe API — is an integer count of minor units (cents, pence, yen). Floating
point never touches a payment amount.

Use the helpers in `@veripay/shared`: `money()`, `addMoney()`,
`multiplyMoney()`, `allocateMoney()`. Convert user input with
`parseMajorToMinor()`, which accepts a **decimal string only** — it will not
take a `number`, because `0.29 * 100` is `28.999999999999996`. New database
columns storing money must be `integer`/`bigint`, never `numeric` or a float.

### Auth0 owns authentication; VeriPay owns authorization

Auth0 establishes **who** the caller is: it issues and signs the access token,
and the API verifies that signature and audience. What that caller is
**allowed to do** is VeriPay's decision, made against VeriPay's own data — is
this user a party to this deal, is the deal in a state that permits this
action. Never treat an Auth0 claim, role or scope as an application
permission, and never authorize an action on the strength of a valid token
alone.

### Stripe webhooks are authoritative for payment state

A payment's state changes only when a **signature-verified Stripe webhook**
says it has. The user being redirected back from Checkout means the browser
came back — nothing more. Never mark a payment captured, a deal funded or a
payout sent from a client redirect, a client-supplied parameter, or an
optimistic UI action. Webhook handlers must be idempotent: Stripe retries, and
the same event will arrive more than once.

### Stripe Projects provisions infrastructure; it does not process payments

The Stripe Projects CLI is how this repository obtains third-party
infrastructure — the Supabase database, and future services. It is a
provisioning and credential tool. It is **not** part of the payment path. Money
movement goes through the Stripe payments API (Checkout, Connect) using
`STRIPE_SECRET_KEY`, which is an entirely separate concern.

### VeriPay is not a regulated escrow service

Do not describe VeriPay as escrow, an escrow service, a trust account, or any
other legally regulated financial arrangement — not in UI copy, marketing,
documentation, code comments, or identifiers. It is a conditional-payment
platform built on Stripe Connect. Funds are held and moved by Stripe under
Stripe's terms; VeriPay does not take custody of user funds and makes no
regulated financial guarantee.

## Database connections

Supabase exposes this project through two connections that are **not**
interchangeable:

| Variable              | Port | Use                                                                   |
| --------------------- | ---- | --------------------------------------------------------------------- |
| `SUPABASE_POOLER_URL` | 6543 | API runtime client. Transaction pooler; prepared statements disabled. |
| `SUPABASE_DB_URL`     | 5432 | drizzle-kit migrations only. Direct connection, needed for DDL.       |

`parseRuntimeDatabaseConfig()` and `parseMigrationDatabaseConfig()` each
hard-require their own variable and reject the other one's port. There is no
generic `DATABASE_URL`; do not introduce one.

## Test expectations

- New route → a Supertest case in `apps/api/src/app.test.ts` (or a sibling)
  asserting status, the response envelope, and the error path.
- New shared logic → unit tests next to it. Money and error mapping carry the
  most risk and get the most cases.
- Tests build their own environment with `loadEnv({ ... })` and pass it into
  `createApp`. No test reads ambient `process.env`, opens a socket to Supabase,
  or calls Stripe.
- Validate responses against the shared Zod schema rather than hand-written
  object literals, so contract drift fails the build.
- `npm run typecheck && npm run lint && npm run test` must pass before work is
  considered done.

## Code standards

- No `any`. If an external boundary genuinely forces it, narrow immediately and
  document why in a comment.
- No `eslint-disable`, no `@ts-expect-error`, no `@ts-ignore`. Fix the cause.
- Errors thrown deliberately are `AppError` subclasses from `@veripay/shared`;
  the error handler turns them into the standard envelope. Do not build ad-hoc
  `res.status(...).json(...)` error responses.
- Log through the injected pino logger, never `console`. Never log tokens,
  secrets, full card data or PII — see the `redact` list in `lib/logger.ts`.
- TypeScript is pinned to 6.0.3 on purpose. See `docs/tooling.md` before
  changing it.

## Rules for agents

- **Do not deploy.** Not to Vercel, not anywhere.
- **Do not commit or push** unless explicitly asked in the current request.
- **Do not rotate, regenerate or print credentials.** Read variable _names_
  from `.env` when you need them; never echo values into the transcript, logs,
  commit messages or documentation.
- **Do not run `stripe projects` provisioning commands** — `add`, `init`, or
  anything that creates or links a resource — without explicit instruction.
  The Supabase project already exists.
- **Do not run migrations** (`db:generate`, `db:migrate`) unless asked. They
  touch the real Supabase database.
- **Do not create Auth0, Stripe, Supabase or Vercel resources.**
- Preserve the Stripe-Projects-managed regions of `AGENTS.md`, `CLAUDE.md`,
  `.gitignore`, `.cursorignore` and `.claude/settings.json`. Merge alongside
  them; never overwrite.
