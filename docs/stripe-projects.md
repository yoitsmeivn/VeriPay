# Stripe Projects

VeriPay uses the [Stripe Projects CLI](https://docs.stripe.com/stripe-cli) as
the control plane for third-party infrastructure. It provisions services, holds
their credentials, and writes the resulting environment variables into the
git-ignored `.env`.

## Stripe Projects does not process payments

This is the distinction that matters most, and it is easy to blur because both
things say "Stripe".

**Stripe Projects** is a provisioning and credential tool. It created the
Supabase database and the Auth0 client. It is infrastructure plumbing and sits
entirely outside the payment path.

**The Stripe payments API** (Checkout, Connect) moves money, using
`STRIPE_SECRET_KEY`. None of it is implemented yet.

Provisioning a resource through Stripe Projects has no billing consequence for
VeriPay's users and creates nothing on a customer's behalf.

## Generated environment variables

**Names only.** Values live in `.env` (git-ignored) and
`.projects/vault/vault.json` (git-ignored). Never print, log, commit or paste a
value — `stripe projects env` redacts them by default, and that default should
never be worked around in a report or a transcript.

**Supabase — `veripay`**

| Name                       | Role                                                  |
| -------------------------- | ----------------------------------------------------- |
| `SUPABASE_POOLER_URL`      | Transaction pooler, port 6543 — API runtime client    |
| `SUPABASE_DB_URL`          | Direct connection, port 5432 — drizzle-kit migrations |
| `SUPABASE_DB_PASS`         | Database password                                     |
| `SUPABASE_PROJECT_REF`     | Project reference                                     |
| `SUPABASE_PROJECT_URL`     | Supabase API URL                                      |
| `SUPABASE_PUBLISHABLE_KEY` | Publishable (client-safe) key                         |

**Supabase — `supabase-plan`:** `SUPABASE_ORG_SLUG`, `SUPABASE_PLAN`

**Auth0 — `veripay-spa`**

| Name                  | Role                                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| `AUTH0_DOMAIN`        | Tenant domain — also copied to `VITE_AUTH0_DOMAIN`                                                                            |
| `AUTH0_CLIENT_ID`     | SPA client id — also copied to `VITE_AUTH0_CLIENT_ID`                                                                         |
| `AUTH0_CLIENT_SECRET` | Confidential-client credential. **Unused by VeriPay** — the SPA flow is public-key only. Never copy it to a `VITE_` variable. |

`AUTH0_AUDIENCE` is **not** generated by Stripe Projects. The catalog has no
API/resource-server service, so it is created by hand in the Auth0 dashboard.
See [auth0.md](./auth0.md).

## Conventions

**Prefix Auth0 commands with `DEV_MODE=true`**, per the generated `sp-auth0`
skill.

**Inspect the live catalog before provisioning.** Never guess a
`provider/service` slug:

```bash
stripe projects catalog auth0 --json
stripe projects catalog supabase --json
```

The catalog is authoritative — it tells you whether a service is a `plan`, a
`deployable`, or a `component` that requires a parent plan. `auth0/client` is a
component, which is why `auth0/free` had to be added first.

**Never edit `.projects/` by hand.** `state.json`, `state.local.json`, `cache/`
and `vault/` are all CLI-managed. Use the CLI or change nothing.

**The CLI rewrites `.gitignore`** on every `stripe projects add`, and may move
its block within the file — it relocated its rules from the top to the bottom
when Auth0 was added. Leave those lines wherever they land and keep VeriPay's
rules in the marked `# --- VeriPay ---` block.

**`AGENTS.md` and `CLAUDE.md` contain managed marker blocks**
(`<!-- stripe-projects-cli managed:* -->`). The CLI regenerates the region
between the markers. Add content strictly outside them. Both files are in
`.prettierignore` because Prettier inserts blank lines inside those markers.

**Generated skills** land in `.agents/skills/` (`sp-supabase`, `sp-auth0`,
`stripe-projects-cli`) with symlinks under `.claude/skills/`. They are
regenerated by the CLI — read them, do not edit them.

## Useful commands

```bash
stripe projects status              # providers, services, plans
stripe projects env                 # variable names, values redacted
stripe projects env --pull          # write values into .env (git-ignored)
stripe projects catalog <provider> --json
stripe projects open <provider>     # provider dashboard, for manual steps
```

## Rules for agents

- **Do not provision anything without explicit instruction.** Supabase and
  Auth0 already exist; a second `add` creates a second billable resource.
- **Do not provision ElevenLabs.** It is account-linked but intentionally not
  part of this project.
- **Do not run `stripe projects env --pull` output into a transcript**, a log, a
  commit message or documentation.
- **Do not rotate or regenerate credentials.**
- Read variable _names_ when you need them (`grep -oE '^[A-Z_]+' .env`), never
  values.
